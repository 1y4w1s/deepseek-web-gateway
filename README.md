# DeepSeek Web Gateway（Windows 一键本地部署）

这是一个**独立的本地启动器**，复用开源项目 [dekrezz/FreeDeepseekAPI](https://github.com/dekrezz/FreeDeepseekAPI)，把个人登录的 DeepSeek 网页会话提供为 OpenAI 兼容 API，供 DeepSeek Harness（DSH）或其他本机客户端调用。

本仓库只包含启动脚本，**不包含账号、Token、Cookie、浏览器资料或运行日志**。首次启动时自动从上游 `stable` 分支下载程序。

> 非官方实验性项目，不保证无限额度、长期可用或与 DSH 原生工具调用完全兼容。DeepSeek 网页接口变化可能导致不可用，请留意服务条款和账号使用风险。本项目仅为个人本机使用准备。

## Windows 部署

**前置条件：** Node.js 18+、Git、Google Chrome，以及可以访问 `https://chat.deepseek.com` 的网络。

1. 在 GitHub 选择 **Code → Download ZIP**，然后**完整解压**到固定文件夹；或用下面的 Git 命令克隆。
2. 双击仓库根目录的 **`Start.vbs`**。
3. 首次启动自动下载上游程序；在 Chrome 窗口中登录**当前电脑自己的** DeepSeek 账号，并按登录窗口提示操作。
4. 登录成功后启动本地 API 并打开管理页面；同时会在 Windows 桌面创建 **DeepSeek Web API** 快捷方式。
5. 后续双击快捷方式即可复用已有服务，不需要重新克隆，正常情况下也不需要重新登录。

```powershell
git clone https://github.com/1y4w1s/deepseek-web-gateway.git
```

不要在压缩包预览界面直接双击 `Start.vbs`；部署后不要随意移动仓库目录，否则桌面快捷方式将失效。

### Windows 系统代理与 Node 网关出口对齐（2026-11-03）

实机发现：Chrome 登录使用了 Windows 已启用的本地 HTTP 代理，而启动器的 Node.js 原生 `fetch()` 没有设置 `HTTPS_PROXY` / `NODE_USE_ENV_PROXY`，因此网页与网关可能走不同出口。现有启动器在 **Windows 启用本地 `127.0.0.1:端口` 或 `localhost:端口` HTTP 系统代理**时，将代理地址传给**网关子进程**并启用 Node 环境代理；同时将 `127.0.0.1,localhost` 列入 `NO_PROXY`。不会修改 Windows 系统代理、登录文件或 DSH 配置。

此最小匹配不覆盖 PAC、SOCKS、远程代理及复杂的分协议代理字符串；若系统代理使用其他形式，仍使用原有行为。Node.js 24 支持环境代理，但需要显式启用。切换系统代理端口后，应重新启动本地网关进程以重新读取端口；仅打开 Dashboard 不会热更新。

证据：本机代理至 `chat.deepseek.com:443` 的 HTTP CONNECT 返回 200；Node 环境代理本地模拟测试通过，两种启动器的 PowerShell AST 语法检查均无错误。**这些测试验证的是出口配置与请求转发，不代表账号认证已恢复。** 之前的 `401 INVALID_TOKEN` 可能还有 Token 失效、上游策略或网页接口变化等原因；真实开发长任务仍待验证。

### Chrome 登录态有效性验证（2026-11-03）

现有登录入口 `Authenticate.ps1` 会先应用兼容补丁，再运行上游的 Chrome 登录脚本。新的登录脚本在**替换本地凭证文件之前**，使用同一个 DeepSeek Chrome 页面的会话凭证，向 `POST /api/v0/chat/create_pow_challenge` 发送**仅一次**认证验证请求（目标为补全接口，不发送聊天消息）。只有 HTTP 与业务状态均成功时才保存新凭证；遇到 `401`、业务拒绝、网络错误、超时或误打开其他网站时，保留原登录文件并报告失败。验证有超时上限，不在失败时循环重试。

## GitHub 源码读取与网页桥接兼容性

本仓库新增一个极小的**上游兼容补丁**：启动时运行 `patches/apply-upstream.cjs`，只更正 FreeDeepseekAPI 在工具说明、工具提醒和异常恢复中对联网能力的冲突描述。

- 在 `-nosearch` 模型下，如果 DSH 真正提供 `websearch`、`webfetch` 或类似工具，网关不再提示模型禁止调用这些已提供的工具。
- 要查看 **GitHub 仓库源码**，优先让 DSH 使用已授权的 Git/终端工具，在独立目录执行 `git clone` 并实际读取文件；网页搜索结果不能代替源码文件。
- 如果 DSH 根本没有提供联网、Git 或终端工具，这个补丁不会创造它们，也不能修复 DNS、代理、GitHub 访问受限的问题。
- DSH 的 `web_search` / `web_fetch` 要求自身装载对应工具、且选择的搜索/抓取服务就绪；`-nosearch` 只关闭 DeepSeek 网页搜索，不会自动安装 DSH 联网工具。没有这些工具时，可先改选 `deepseek-v4-flash-thinking` 使用 DeepSeek 网页搜索，但要验证 GitHub **源码文件**仍需实际 Git/终端读取。
- 当使用带搜索的模型时，DeepSeek 网页搜索仍由 DeepSeek 端实现；需要可验证的源码文件时仍应使用 DSH 工具。

补丁是幂等的；上游代码发生不兼容变更时会**停止启动并给出错误**，不会默默假装已经修复。排查 `runtime/patch.stderr.log`。

安装并完成首次运行之后，可以在仓库目录运行回归测试：

```powershell

```

测试涵盖：新旧提示矛盾、GitHub 源码访问指引、工具恢复提示、补丁重复执行和上游变更时的明确失败。**这不等于完成 DSH 真实工具调用验收。**

注意：若启动时检测到本机 **9655 已经运行**，启动器会直接打开控制台，不会热替换当前进程中的代码。需要应用新版本补丁时，先正常停止属于该网关的进程，再启动；不要批量终止其他 Node 进程。

## DeepSeek 网页限流：15 秒起始节奏（2026-11-03）

实际 DSH 工作流中出现约 13 轮网页消息和至少 3 次额外工具格式修复请求，短间隔连续调用后，DeepSeek **网页端**通过 HTTP 200 的消息流返回“消息太频繁”。网关把该账号标记为限流并按本地默认值冷却 600 秒。**600 秒不是官方网页额度的公开承诺**，也不能拿 DeepSeek **官方 API** 的并发额度来套用网页登录接口。

在本项目的上游兼容补丁中，已加入最小的**按账号发送节奏**：同一账号的两次 `/api/v0/chat/completion` 请求开始时间至少相隔 **15 秒**（理论最高约 4 次/分钟）。首次请求不延迟，现有账号锁继续保证同账号同一时刻最多一个请求；会话续办、格式修复和因会话失效产生的二次 completion 也计入节奏。**本地工具执行、Git 命令、文件读取以及网页内容回传都不降速**。

这个数值是基于本轮失败观察选择的**保守试验值，不是已验证的安全阈值**，仍可能由于平台动态配额、累计用量和服务负载触发 429。如果仍然限流，应先遵守返回的冷却时间，减少无谓的工具轮次，而不是重启进程、换账号或循环重试来清除限制。浏览器网页服务可能对自动化存在额外限制。

本轮：补丁/回归 **8/8 PASS**。等候本机原账号冷却自然结束后，正常重启了 `127.0.0.1:9655` 网关，并进行了两次连续真实请求：第一次 HTTP 200（2.45 秒），第二次 HTTP 200（14.96 秒），总计 17.42 秒，验证限速确实生效，测试结束账号未重新进入冷却。**这是短程节奏验收 PASS，不代表长时间高负载下 429 已被彻底消除**。另一台电脑更新仓库后，正常关闭旧网关再用 `Start.vbs` 加载新补丁；首次部署仍需单独验收。

### 401 认证阻断与 429 冷却分离（2026-11-03）

真实失败：上游返回 `401 INVALID_TOKEN` 后，旧网关只冷却 600 秒，期满自动视为可用，导致 DSH 下一轮重复 401。本轮**复用现有账号状态机**，按故障类别处理：

- **401**：当轮仍返回 401；对应登录状态在当前网关进程内标记为认证阻断。即使普通 600 秒冷却到期，也不会自动重新使用同一凭证；Dashboard 的 `disabled_by` 标记为 `auth`。
- **恢复**：运行 `Authenticate.ps1` 完成网页登录并保存新 token/cookie，然后 Dashboard → Accounts → Reload accounts；只有凭证内容真正发生变化才自动解除阻断。单纯刷新网页、重启 DSH、重新加载相同文件都不解除该进程内的阻断。重启网关会重建运行时状态，**不代表上游凭证有效**。
- **429**：仍保留原有限时冷却、服务端 `Retry-After`、独立账号请求锁，不增加或降低 15 秒间隔。
- **403**：沿用上游原有短期冷却逻辑，未擅自视为永久无效 Token。
- **账号池**：其他凭证有效的账号继续可服务；账号指定请求得到明确的 `auth_expired` 401。所有登录均处于认证阻断时，返回 `auth_expired` 401，而不是错误宣称 429。
- **后台操作**：对认证阻断账号按“清除冷却”返回 409 `auth_expired` 并提示重新登录；避免页面误报恢复。

验证：新增认证与冷却专项 **7/7 PASS**，已有兼容和工具协议 **16/16 PASS**，上游解析器专项 **43/43 PASS**；上游 `account-failover` 定向两项 PASS。其完整回归由于已加入的 15 秒等待会使模拟测试长时间运行，已主动停止，不能宣称整个上游测试全 PASS。真实网页认证/完整 DSH 长任务本轮 **NOT_RUN**，离线测试通过不能保证网页 Token 被 DeepSeek 接受。
### 账号被限制数日时：本地止损与有效吞吐（2026-11-03）

如果官方网页已经明确显示账号被禁言数日，请遵守限制；Dashboard → Accounts 可**手动 Disable 当前受限账号**，到限制解除后再由本人确认并 Enable。仅在确定是该账号时操作。`/health` 或 `/admin/accounts` 显示 Ready 只表示本地保存了凭证，不是官方网页解除禁言的证明。不要清除冷却、反复重登、轮换账号来试探限制。

本网关已经复用原有会话增量续聊、认证阻断与 Retry-After 冷却逻辑，不新建缓存/重试管理器。**离线回归**：模拟 HTTP 429 且 `Retry-After: 259200`（3 天），连续两次尝试选用该账号均被网关本地拒绝，未重新放行上游请求；本仓相关测试 **32/32 PASS**。如果私有网页接口没有返回明确 Retry-After，网关不会凭猜测识别“禁言三天”，仍使用默认冷却，因此需要官方网页状态和手动暂停操作。

进一步定位（同日）：**两次 HTTP 请求不是一次模型生成的重试**。在合成的 429 测试里，第一份请求有 25 个工具、最大输出 32768；约 1–2 毫秒内并发的第二份请求没有工具、最大输出 4096。源码查重确认 DSH 的 `session-title-llm` 会为新会话另发一次模型标题生成请求。单独禁用该插件后，即使保留 `maxRetries: 1`，本地请求也从 **2 次变为 1 次，隔离验收 PASS**。因此不需要盲目修改 DSH 的错误重试策略，更不需要增加网关拦截器。

对于**只用于 DeepSeek Web Gateway 的 DSH profile/启动 `--patch`**，可追加以下现有插件关闭项（请勿重复声明同一个 `id`）：

```yaml
- id: session-title-llm
  disabled: true
```

关闭的是模型辅助命名调用；DSH 仍可根据第一条用户消息生成本地回退标题，不影响主任务、工具调用和会话日志。此设置作用于**整个被应用的 DSH profile**，因此不自动写入日常 desktop profile（它也可能包含其他模型提供方）。本机已仅写入两个隔离网关用例的 patch：`acceptance/dsh-coding.patch.yml` 与 `publish/tests/dsh-headless.patch.yml`。所有证据来自本地模拟 429，不是被禁言账号的真实恢复测试。不要利用自动化绕过账号限制。

这说明持久化远端会话关联有潜在价值，但节省的是**重启后的首轮上下文重传**，不是官方 API 的 token/s 或额度提升。模拟恢复记录仅有约 221 字节元数据，**尚未实现或部署任何磁盘持久化**，也没有证明旧 DeepSeek Web 会话实际接受重连。

**实施门槛：** 旧会话需绑定确切账号与当时登录凭证状态；账号重登、被限制、被删除、会话超过现有两小时 TTL 或 100 消息阈值时不能误恢复；服务器重启和真实 DSH 历史回传需独立验收。特别注意当前运行中的账号重登会丢弃旧会话，跨进程恢复不能丢失这项保护。用户受限账号未被调用，现有运行服务和凭证均未改动。本轮裁决：先留 A/B 回归，**暂缓持久化产品改动**。

### 工具输出冗余与压缩 A/B（2026-11-03，离线）

针对现有 `formatMessages`、`resolveUpstreamPrompt`、`buildBoundedPrompt` 新增合成测试 `tests/offline-tool-output-ab.test.cjs`。8 轮、每次约 9,000 字符工具输出时，正常 Sticky 续聊只向模型发送最新结果 **9,016 字符**；重建会话时是 **72,917 字符**。约 19 KB 的新错误堆栈可完整保留；108 KB 的超大工具输出会自动压缩到 **80,000 字符**。同一结果由工具再次产生时仍会发送最新一次约 23 KB 内容，**不能因文本相同就猜测属于重复结果并删除**。

另一个合成边界：若客户端历史缺少 Assistant 消息分隔，增量选择器可能连同之前的工具输出一起重传（示例约 24 KB）。目前缺乏真实 DSH 消息结构证据，暂不改动该逻辑。**本轮仅交付测量，不新增裁剪器/缓存/状态管理器**，避免意外丢失堆栈尾部和重要诊断结果。5 项工具输出测量全部通过，连同原有测试合计 **45/45 PASS**；账号限制期间没有真实 DeepSeek 上游调用，字符数不是 Token 数，也不是吞吐量提升实测。

## 限流与 DSH 重试（可选配置，不自动修改 DSH）

真实任务中曾发生：DSH 成功 `git fetch` 且 `HEAD` 与远程分支一致，但继续请求模型后触发网页端 600 秒限流；DSH 默认对 `RATE_LIMIT` 重试五次。这个网关无法替 DSH 消除客户端自有的重试策略。**可在 DSH 已有的 `llm-pi-ai` → `providers` → `deepseek-web-local` 条目内**添加下列配置（不要另建第二个同 ID 的 patch entry）：

```yaml
retryPolicy:
  mode: normal
  maxRetries: 1
  retryableCodes: [EMPTY_RESPONSE, SERVER, TIMEOUT, TRANSPORT]
```

这保留了其他临时故障最多一次重试，但**遇到 RATE_LIMIT 立即向用户报告**，避免在 10 分钟冷却期内重复轰炸网页登录会话。其它模型提供方的策略不受影响。此配置需要在另一台电脑的 DSH 自行选择应用；独立网关安装脚本不会写 DSH 配置。

来源：DeepSeek Harness 官方 `packages/llm/llm/src/retry-policy.ts` 与 `packages/llm/llm-retry/README.zh.md`。

## 文件与排障

- `Start.vbs`：一键入口，并在首次运行时创建桌面快捷方式。
- `Start.ps1`：检查现有服务、下载上游、触发登录并启动服务。
- `Authenticate.ps1`：首次人工浏览器登录。
- `.gitignore`：排除运行目录、日志及可能的密钥文件。
- `runtime/upstream/`：首次运行后创建的上游源码、登录状态和浏览器数据；**严禁上传**。
- `runtime/launcher.log`：启动错误，发生错误时自动用记事本打开。
- `runtime/git.stderr.log`：Git 下载错误。
- `runtime/server.stderr.log`：API 服务错误。
- `runtime/server.pid`：启动进程 PID。停止时要核实进程归属，不要批量结束所有 `node.exe`。

若网页登录失效，在本仓库文件夹打开 PowerShell，执行 `./Authenticate.ps1` 重新登录。健康检查的 HTTP 200 仅证明 API 启动，不等于 DSH 的真实工具链通过。
